# ByteTide 功能缺口调研

更新时间：2026-09-09

## 结论

ByteTide 已经不是“只有串口终端”的工具：当前已有多会话、TCP/UDP、虚拟日志滚动、HEX/ANSI、搜索过滤、规则告警、自动回复、触发式捕获、解析脚本、实时绘图、对比、离线复盘、CLI 和 REST 桥。

因此，下一阶段最有价值的功能不是继续堆基础控件，而是把它从“强大的调试台”推进到“可重复的协议测试与数据复盘工具”。建议优先顺序为：

1. 协议测试工作流（步骤、断言、变量、失败现场）
2. 可控回放与发送仿真
3. 更完整的协议/传输支持
4. 会话数据库、标签和报告
5. 文件传输与串口控制能力

## 同类产品对照

### Serial Studio

Serial Studio 的公开功能包括多种总线驱动（Serial、TCP/UDP、BLE、MQTT、Modbus、CAN、OPC UA 等）、20+ 仪表盘组件、JavaScript/Lua 解析、CSV/MDF4/SQLite 记录、会话回放、HTML/PDF 报告、Control Loop 自动化和 X/Y/FFT/瀑布图等。

参考：[官方功能页](https://serial-studio.github.io/)、[数据记录与回放](https://serial-studio.com/blog/data-logging-and-session-replay)、[Data Flow](https://github.com/Serial-Studio/Serial-Studio/blob/master/doc/help/Data-Flow.md)

ByteTide 已覆盖：实时日志、基础波形、解析脚本、CSV/TSV 记录、离线打开、REST 自动化入口。

ByteTide 的明显差距：

- 没有真正的会话数据库、标签、收藏和跨会话检索；
- 没有拖动时间轴、倍速、暂停/继续、按原始时间间隔回放；
- 没有 HTML/PDF 报告；
- 绘图组件仍以基础时序图为主，缺少 FFT、XY、频谱瀑布、仪表盘控件、地图等；
- 没有可持久化的 setup/loop 控制脚本。

### Docklight

Docklight 面向串口协议测试，核心是发送序列、接收序列匹配、动作触发、脚本化测试以及错误前后自动快照；同时支持 ASCII 和二进制数据的日志记录。

参考：[Docklight Overview](https://docklight.de/manual/docklightoverview.html)、[Scripting Manual](https://docklight.de/pdf/docklight_scripting_manual.pdf)

ByteTide 已有：快捷帧、发送序列、自动回复、告警、现场捕获。

主要缺口：

- 发送序列还不是“测试用例”：缺少期望响应、超时、重试、断言、变量和通过/失败结果；
- 自动回复偏规则引擎，缺少多步状态机和上下文变量；
- 现场捕获已有触发能力，但还没有把触发前后的数据自动绑定到一次测试结果；
- 没有“虚拟设备/协议模拟器”模式，用于在没有真实设备时主动应答。

### RealTerm

RealTerm 强调困难二进制流调试，提供二进制显示、不同数值类型解释、控制线状态、定长/定时捕获、自动命名、发送二进制序列、网络回显、命令行控制和脚本接口。

参考：[RealTerm 官方页面](https://realterm.sourceforge.io/)

ByteTide 已有：HEX、原始字节、DTR/RTS、分段录制、CLI、TCP/UDP。

主要缺口：

- 缺少 7/8 位、奇偶校验、停止位、流控、break、低级串口控制和控制线输入状态的完整面板；
- 缺少“按定长/定时/同步字节”捕获，而不仅是按行和规则触发；
- 缺少原始二进制文件发送、发送文件进度和限速；
- 缺少一个可脚本化的命令行/IPC 控制面，用于驱动已打开的桌面会话。

### Tera Term / 通用终端工具

传统终端工具的长期优势是终端仿真和宏自动化，例如 Tera Term 的宏语言，以及 Telnet/SSH 等远程终端连接。

参考：[Tera Term 概览](https://en.wikipedia.org/wiki/Tera_Term)

这部分不是 ByteTide 必须全面追赶的方向，但如果目标用户包含设备启动和远程维护场景，可以考虑加入“串口终端模式”和 SSH/Telnet 连接，而不是只呈现结构化日志。

## 建议新增功能

### P0：协议测试用例与断言

在现有“序列”之上增加测试语义：

- 步骤类型：发送 ASCII、发送 HEX、等待匹配、等待解析字段、延时、DTR/RTS、清空缓冲；
- 断言：文本/正则/HEX 掩码/字段值范围/响应时延；
- 变量：`${last.temp}`、`${counter}`、`${timestamp}`，支持把解析结果填入下一步；
- 超时、重试、失败后停止/继续；
- 结果：通过、失败、超时、跳过，附带失败行号和捕获文件；
- 批量运行和结果导出 JSON/CSV。

这是最值得做的差异化能力，因为现有发送序列、解析器、自动回复、告警和捕获都可以复用。

### P0：时间轴回放与发送仿真

- 离线日志按原始时间间隔、固定倍速或单步回放；
- 回放期间复用现有解析、绘图、告警和对比管线；
- 支持把回放数据发送到串口/TCP，提供预览、限速和停止保护；
- 回放状态持久化：当前位置、倍速、循环次数；
- 通过回放生成测试基线，用于回归比较。

这会把现在的“打开日志”从静态查看升级为可重复实验。

### P1：协议与传输扩展

建议按用户价值分批：

1. Modbus RTU/TCP：寄存器轮询、功能码解码、异常码显示；
2. BLE GATT：服务/特征发现、读写和通知订阅；
3. MQTT：订阅/发布、TLS、主题过滤；
4. CAN + DBC：导入信号定义并显示解码值；
5. SSH/Telnet：设备启动日志和远程维护。

不要一开始同时接入所有总线；优先 Modbus 或 BLE，取决于目标用户群。

### P1：会话数据库与报告

- SQLite 会话索引：时间、设备、连接配置、标签、异常数、文件路径；
- 多会话全文/正则/时间范围检索；
- 收藏一次测试运行，保存配置快照和解析器版本；
- 一键生成 HTML 报告，包含统计、图表、告警、差异和关键行；
- 报告可脱敏后分享。

可以保持 TSV/LOG 作为开放交换格式，SQLite 只负责索引和复盘元数据，避免锁定用户数据。

### P1：设备模拟器与回环调试

- TCP server 多客户端；
- UDP 对端发送；
- 虚拟串口或 loopback 端；
- 按脚本/序列响应请求；
- 内置常用故障注入：延迟、丢帧、重复帧、乱码、CRC 错误、断连。

这会显著降低没有实物设备时的开发成本，也能为自动化测试提供稳定 fixture。

### P1：文件传输和大块数据工具

- XMODEM/YMODEM/ZMODEM；
- 原始文件发送/接收，进度、速率、校验和、断点/失败重试；
- 对大文件采用流式读写，不把整个文件放进前端内存；
- 传输过程单独记录到会话时间轴。

这是 RealTerm/Serial Studio Pro 类工具常见、但当前 ByteTide 尚未覆盖的实用能力。

### P2：更丰富的可视化

- FFT、频谱瀑布、XY 散点；
- 仪表盘卡片：Gauge、Bar、LED、Compass、状态矩阵；
- 多坐标轴、单位换算、阈值带、事件标记；
- 绘图配置导入/导出为独立项目文件。

建议先做 FFT + XY + Gauge 三个高复用组件，避免一开始建设完整的可视化编辑器。

### P2：低级串口控制和终端兼容

- RTS/CTS、DTR/DSR、DCD/RI 等输入状态；
- break、线路状态变化事件；
- 7-bit/8-bit、奇偶校验、软件/硬件流控等完整参数；
- 可选 VT100/ANSI 终端模拟模式；
- 终端回显、行编辑、粘贴保护、发送文件快捷入口。

这类功能对“协议日志分析”不是核心，但对现场设备维护很有价值。

## 暂不建议优先实现

- 立刻覆盖 CAN、OPC UA、S7、EtherNet/IP、IEC 104 等全部工业协议；维护成本和测试矩阵会快速膨胀。
- 立刻做完整可视化拖拽编辑器；应先验证 FFT/Gauge/XY 的使用频率。
- 把 REST 桥直接扩张成大型远程控制平台；先完成协议测试、权限和审计，再扩大写操作。
- 放弃现有 TSV/LOG 开放格式，直接把所有数据迁移到专有数据库。

## 推荐路线图

### 近期版本

- 测试用例模型和 runner；
- 等待/断言/超时/重试；
- 测试结果和失败现场绑定；
- 离线按时间轴回放；
- TCP/UDP 模拟器与故障注入。

### 中期版本

- SQLite 会话索引；
- HTML 报告；
- Modbus 或 BLE；
- 原始文件发送与 XMODEM/YMODEM；
- FFT、XY、Gauge。

### 后续版本

- CAN/DBC；
- SSH/Telnet；
- 完整终端仿真；
- 多人/远程协作与受控部署。

## 最小可行切片

如果只选一个功能做下一迭代，建议是“协议测试用例 v1”：复用当前快捷帧、发送序列、解析器、告警和现场捕获，新增等待匹配、超时、断言、重试和结果面板。它能直接覆盖开发、回归测试、现场复现三个场景，也最容易形成 ByteTide 自己的产品辨识度。
